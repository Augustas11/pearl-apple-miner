# F2 result: native job prep (pmkcore) on Apple M5

Date 2026-10-02 · MacBook Air M5 (Mac17,3; 4 P + 6 E cores; 10-core GPU) · macOS 26.5 · AC power · Low Power off.
Code: `pmkcore/` (Rust crate, C ABI `include/pmkcore.h`), `bench/f2_jobprep/` (README has the commands).
Raw output: `bench/evidence/f2_jobprep_m5.txt`.

## Verdict: **F2 PASS at the recommended default 8192 × 8192 × k (k ≥ 4096; F3 picks k)**
- **The GPU did not wait at m = n = 8192.**
  - End to end over 350 jobs, P2 = 0.990 at 8192²×4096. Per round it was 0.95–1.04, and the GPU was 100% busy in every pipelined round.
  - At 8192²×{2048, 8192} the first run gave P2 = 1.17 and 1.01.
  - Measured against the 19 TOPS idle rate, the CPU build takes 0.28–0.33× the GPU time (T = 9).
- **4096² is marginal and not recommended as the default.**
  - At 4096²×2048, aggregate P2 is 0.82 (0.70 in the first run). The first pipelined round of each run reproducibly drops to ~0.37–0.41; later rounds are ≥ 0.89.
  - At 19 TOPS the build would take 0.65× the GPU time. That passes the 0.8 rule with little headroom on a loaded machine.
- **Correctness: byte-identical to zk-pow.**
  - 24 jobs come from zk-pow's own reference miner. For each, A and B were generated by `try_mine_one` with Salted (cert v3) derivation. Its PlainProof roots and the seeds from its verifier path (`parse_proof` → `commitment_hash`) equal pmkcore's.
  - 26 pmkcore-generated jobs match as well. Their roots equal `pearl_blake3::MerkleTree` over the bytes written, and their seeds equal zk-pow's. With A fixed and B fresh, no seed repeats.

## What one job build is
- **Bᵀ.** Fresh, n×k row-major, int8 in [-64, 64], written straight into caller memory (a shared `MTLBuffer` in the P2 run). There are no copies and no Python per byte.
- **CSPRNG.** AES-128-CTR on the ARMv8 AES unit, with a fresh 128-bit key from `getrandom` per job.
- **Commitment.** The keyed BLAKE3 Merkle root under `job_key`.
  - Generation and hashing are fused per 64 KiB segment on a rayon pool.
  - Segment chaining values merge via `blake3::hazmat` into a root identical to `pearl_blake3`'s.
- **Seeds.** `bind_root_b(root_b, n)` → `b_noise_seed` → `a_noise_seed` with the cached `bind_root_a(root_a, m)`, as in `mine.rs:442-479` and `seed.rs`.
- **A.** Fixed per template and built once. That takes 8–23 ms for m ∈ {4096, 8192} and k ≤ 8192, which is negligible per template.

## Caveats (read before quoting)
- **The machine was shared and loaded.**
  - CPU batch: the 1-min loadavg was 12.4 at the start. The bench waited 6 min for ≤ 8, then 28 min for the GPU lock, and loadavg had risen again by the time it ran. **Flag: started above 8.**
  - P2 runs: loadavg 3.7–8.4.
  - Absolute GPU rates were 5–10 TOPS, not 19. With a 2–4× slower GPU, the CPU has more slack than it would on an idle machine. The 19 TOPS ratios above are the conservative check, and they pass at 8192².
- **P2 > 1 is noise, not speedup.**
  - The baseline keeps 2 command buffers in flight and the pipeline up to 3.
  - The SoC's power sharing also moves the GPU clock.
  - Read the P2 values as "≈ 1, GPU never starved", not as a gain.
- **The 4096² first-round dip reproduced across both runs and is unexplained.** It survived pre-touching the slots, and GPU busy still read ~100%, so it looks like a GPU clock or power-state transition rather than starvation. The production loop should warm up before measuring.
- **This proxy excludes K1/K2 (noise, ≤ 10% of K3 by budget) and the K3 BLAKE3/compare.**
  - Both run on the GPU and lengthen GPU time per job, so they only add CPU slack.
  - Memory-bandwidth contention between the CPU build (4 GB/s write+read) and the GPU is included in the measurement.
- **Fanless MacBook Air.** P2 ratios count; absolute rates and sustained behaviour need a fan-cooled Apple10 machine (SPEC §8).

## Recommendation
- **Default shape:** m = n = 8192, with k chosen by F3 (≥ 4096 preferred; 2048 also passed, P2 1.17).
- **Threads:** pmkcore with 9 threads, 3 Bᵀ slots (64 MiB each at k=8192), and A built once per template.
- **4096²:** usable only with k ≥ 4096 and on a quiet machine.
- **Python:** never touches matrix bytes. ctypes releases the GIL during `pmkcore_build_job`, which is one call per job.
